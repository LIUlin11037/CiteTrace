# Cite Trace — 架构文档与技术选型

> 版本：v0.1（定稿）｜ 定位：简历级工程项目 ｜ 语言：Python 3.12+

## 1. 项目定位

面向 **AI / 科技行业调研** 垂直场景的多智能体深度研究系统：输入一个研究课题，系统自动拆解子问题、并行取证（arXiv / GitHub / Web）、审校证据、生成带引用的中文研究报告。

架构保持 domain-agnostic——垂直性只体现在数据源配置与提示词，换题材不改代码。

## 2. 技术选型与理由

| 层    | 选型                                                    | 理由                                                                  | 备选（未选原因）                      |
| ---- | ----------------------------------------------------- | ------------------------------------------------------------------- | ----------------------------- |
| 编排   | **LangGraph**                                         | 状态机图、checkpointer 断点续跑、`interrupt` 原生支持人机回环、Send API 支持动态并行 fan-out | LlamaIndex（编排表达力弱）、纯手写（缺生态共识） |
| 模型接入 | **OpenAI 兼容协议抽象**（langchain-openai + 自定义 base_url）    | 一条代码路径切换 DeepSeek / Qwen / OpenAI / vLLM；按角色分配模型控成本                 | 各厂商 SDK（路径分叉、维护成本高）           |
| 工具生态 | **MCP 协议**（langchain-mcp-adapters）                    | 工具可插拔、server 可独立开发测试；自研 MCP server 本身是加分项                           | 硬编码 tool 函数（扩展性差）             |
| 数据   | **PostgreSQL + pgvector**（检查点与向量检索同库，生产与开发统一）         | 业务持久化与向量检索一个组件搞定                                                    | Milvus/Chroma（多一个组件，运维成本高）    |
| 服务   | **FastAPI + SSE**                                     | 流式输出是 Agent 产品的刚需，SSE 比 WebSocket 简单够用                              | WebSocket（杀鸡用牛刀）              |
| 可观测  | **Langfuse**（M4 接入）                                   | 自托管、trace 每次 LLM/工具调用                                               | LangSmith（绑定云账号）              |
| 评测   | **自建 eval harness**：Golden 题集 + LLM-as-judge + 引用自动验证 | 引用存在性可程序化核验（arXiv ID / 仓库 / URL 可达），指标硬                             | RAGAS（与本系统输出形态不完全匹配）          |
| 工具链  | **uv + ruff + mypy(strict) + pydantic v2**            | 2026 年 Python 工程标配                                                  | poetry / flake8（已被社区淘汰趋势）     |
| 部署   | **Docker Compose**                                    | 一键起全栈，演示友好                                                          | K8s（过度设计）                     |

### 关键取舍说明

- **按角色分模型**：Researcher 高频调用用便宜模型（如 deepseek-chat）跑量，Critic/Writer 用强模型保质——成本与质量的工程平衡，配置层原生支持。
- **结构化输出唯一入口**：所有 LLM 解析走 `with_structured_output`（pydantic 校验），代码库中禁止 regex 解析 JSON。
- **证据先行，写作在后**：Researcher 只记录"来源直接支持的原子事实"，跨来源综合只发生在 Writer——从架构上抑制幻觉。

### 3.1 信源层：两种模式，一套编排

信源差异被压缩到**工具集**这一层，编排/审校/引用核验完全共用：

| | `online`（默认） | `offline` |
|---|---|---|
| 装载的 MCP server | arxiv / github / web | 仅 `kb`（`network: false`） |
| 网络 | 必需 | **不需要**（模型随镜像交付） |
| 引用核验 | URL 存在性（arXiv API / GitHub API / HTTP） | **文件 + 章节**（文件在不在、引的那节在不在） |
| 证据不足时 | Critic 追问 → 再取证 | 追问无效，**代码强制**转成 blocking 存疑项 |

三个刻意的设计约束：

1. **装载前过滤，而非运行时禁用**——`offline` 下网络类 server 根本不会启动，
   "以为离线其实在联网"这种事故在结构上不可能发生；一个本地 server 都没有时
   `get_mcp_tools()` 直接抛错，而不是静默降级成"无工具"。
2. **知识库只存相对路径**（相对 `DR_KB_ROOT`）——绝对路径会让同一份库在容器里
   全部失效（实测：cite/cover 归零）。
3. **追问有出口**——离线无法补证，`follow_up` 会变成死循环；Critic 节点把
   追问转成 blocking 后放行，Writer 必须显式写"当前知识库未收录该信息"。

知识库链路：

```
ingest_kb.py ─ 切块(600 字符/80 overlap，带标题锚点)
     └─ 本地 embedding(bge-small-zh, 512d) → pgvector
检索：向量 + Postgres FTS + 中文字符二元组  → RRF 融合（词法权重 1.5）
     └─ 命中片段带「来源：相对路径 / 位置：标题 · 行号」
取证：Researcher 只接受能定位到本地文件的来源（外部 URL 一律丢弃）
写作：脚注由代码生成 → 核验器读文件校验"章节确实存在"
```

## 4. 编排核心：主流程与状态机

```
START → planner ──interrupt(人工审批/编辑计划)──► fan-out(Send×N)
                                                     │
                                              researcher ×N（并行取证）
                                                     │
                                                   critic ──证据不足且轮次未满──► fan-out(追问 Send)
                                                     │ 通过
                                                   writer → END
```

### 状态通道设计（`agents/state.py`）

| 通道                             | 归并策略            | 写入者          | 说明                             |
| ------------------------------ | --------------- | ------------ | ------------------------------ |
| `evidences`                    | `operator.add`  | Researcher×N | 并行分支只返回增量，由 reducer 合并——全图最易错点 |
| `messages`                     | `add_messages`  | 各节点          | 对话轨迹                           |
| `plan` / `critique` / `report` | last-write-wins | 单一节点独占       | 无并发写                           |

### 四类 Agent 职责边界

- **Planner**：课题 → ≤6 个正交子问题（学术/工程/产业三维覆盖），产出后经 `interrupt` 交人工审批，可编辑后放行。
- **Researcher**：单个子问题的 ReAct 循环（≤8 步工具调用），只提取"来源直接支持的原子事实"，保留原文摘录供核对。
- **Critic**：覆盖度/可信度/一致性/时效性四查；有 blocking 问题则生成追问（follow-up）回环重研，最多 2 轮。
- **Writer**：证据内写作，逐句引用 `[^n]`，证据不足处显式声明，输出带参考来源列表的 Markdown 报告。

### M3 实现要点（`core/persistence.py` + `core/memory.py`）

- **checkpointer 双后端**：`open_checkpointer()` 工厂按 `DR_CHECKPOINT_BACKEND` 切换 **PostgresSaver（默认）** / SQLite（零依赖后备，需显式开启），CLI、API、eval runner 统一走工厂

## 7. 评测指标（M4 已实现于 `src/deep_research/eval/`）

设计原则：**能程序化核验的绝不用 LLM 判断**——可复现、零成本；LLM-as-judge 只负责代码无法判定的部分。

| 指标           | 方法                                                                                                                   | 模块                                  |
| ------------ | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| **引用存在率**    | 纯程序：解析 `[^n]` 脚注 → 按来源类型核验（arXiv API id_list / GitHub repos API / HTTP 可达）。网络故障计为 unverifiable 而非 missing——网络抖动不惩罚指标 | `eval/citations.py`                 |
| **声明-来源对齐率** | LLM judge：抽取带 `[^n]` 的论断（抽样上限 12 条/篇），对照证据 key_points 判 supported/partial/unsupported                                | `eval/judge.py`                     |
| **知识点覆盖率**   | LLM judge：Golden 题集每题带 expected_key_points（可判定的具体事实），judge 逐条分 covered/missed                                        | `eval/judge.py` + `eval/dataset.py` |

- **对齐判定的两个关键设计**：① 论断与其引用来源的匹配走「脚注 → 参考列表 URL → 归一化 → 证据库查找」，

  **不做位置映射**（早期按位置映射导致对齐率虚低）；② 新增 `meta` 判定并**从对齐率分母中排除**——

  报告里「本次未引用 X」「来源与主题无关」这类**方法性说明**不是事实主张，不该按"无依据"扣分
- Golden 题集：`eval/golden/tech_ai.json`，**26 题**（agent 10 / llm 9 / rag 7），每题带 expected_key_points（可判定的具体事实）
- 流水线：`eval/runner.py` 自动批准计划跑图 → 三指标评测 → 聚合出 JSON + Markdown（`reports/eval/`），含按子领域分项；

  失败题自动串行重试，全部失败则直接抛错（不写空摘要）
- 每题**报告与证据库落盘**（`reports/eval/reports/<qid>.{md,evidences.json}`），支持**离线复判**：

  `scripts/rejudge_alignment.py`（单题）、`scripts/refresh_alignment.py`（全量刷新，改 judge 后不必重跑研究）
- **分数回挂**：`eval/scores.py` 把三个指标写成 Langfuse trace score（含注释），可在 UI 按分数筛选并下钻到该次运行
- 实测结果（26 题）：引用存在率 **100%**、论断-来源对齐率 **96.5%**、知识点覆盖率 **100%**；

  两次连跑共 3521 次调用、输入 15.3M tokens，合计 **¥11.05、单题约 ¥0.43**
- 全部外部依赖（图、judge、网络核验）可注入替换，整条流水线可离线冒烟（`scripts/smoke_eval.py`）

### 引用核验的两种强度

同一套核验器接口，按来源类型分派：线上验"URL 返回 200"，离线下验
"文件存在 + 章节命中 + 锚点行号可定位"。后者更硬——URL 可达不代表内容还在，
而文件 + 章节是可复现的。锚点匹配做了规范化（模型抄锚点会截断、换标点、
用 `；` 串多段，逐字匹配会把真引用判成缺失，实测 9/38）。

### 检索层基准（私有语料）

除端到端指标外，另有一条**只看检索**的基准：FinanceBench 21 题（3 份真实 10-K、571 页），
指标是"evidence 所在页是否出现在前 k 条"。它零 LLM 成本、可反复跑，用来判断
"答不出来"到底是检索问题还是阅读问题。

实测：页面命中@10 从 14%（本地中文小模型）升到 57%（多语言模型 + rerank + query 扩展），
召回@50 从 29% 到 90%。结论与数据见 [`检索基准-FinanceBench.md`](检索基准-FinanceBench.md)。

### "没有数据"不等于"得 0 分"

对齐率在抽不到可判论断时返回 `None`（N/A）并从聚合中排除，而不是 0.0。
原因：某题因正文引用格式漂移导致 0 条样例，被记成 0%，一下把三题均值从 90%
拉到 61%；而它的真实值是 86%。指标宁可显示 N/A，也不能编一个 0。

## 8. 可观测性（Langfuse）

一次调研 = **一条 trace**；LangGraph 会把入口处的 callbacks 透传到每个嵌套 runnable，

因此只需在入口挂一次，就能拿到完整的 `graph → node → chat model / MCP tool` 三层 span。

| 维度       | 传递方式                                                   | 用途                                       |
| -------- | ------------------------------------------------------ | ---------------------------------------- |
| trace 结构 | callback handler（入口挂载）                                 | node 耗时、执行顺序、并行 fan-out 分支               |
| tags     | `metadata.langfuse_tags`（保留键）                          | `eval` / `web` / `cli` + 评测题目 id，便于筛选与定位 |
| session  | `metadata.langfuse_session_id` = LangGraph `thread_id` | 把 HITL 中断产生的**多段 trace 归并**为一次完整调研       |
| user     | `metadata.langfuse_user_id`（接口已留，CLI/评测未传）             | 多用户场景下按人聚合与成本分摊                          |
| LLM 明细   | ChatOpenAI span                                        | prompt/response 全文、model、token 用量        |
| 工具调用     | MCP span                                               | 工具名、参数、返回内容                              |
| 质量分数     | `eval/scores.py` → trace score                         | 指标与运行轨迹对齐，可按分数排序下钻                       |

v5 的注意事项（踩过的坑）：session/tags **不是** handler 参数而是 run config 的保留 metadata 键；

入口退出前必须 `flush_tracing()`，否则最后一批事件会被后台导出器丢弃；未配置 key 时全链路旁路、不影响主流程。

## 9. 部署形态（Docker Compose）

`app`（FastAPI/SSE）+ `postgres`（pgvector）两个服务；`app` 通过

`DR_CHECKPOINT_BACKEND=postgres` 与容器网络内的服务名连库，并 `depends_on: service_healthy` 等 PG 就绪。

- **数据层统一 PostgreSQL**：检查点与 pgvector 长期记忆同库，`.env` / 代码默认 / compose 三处一致
- **Dockerfile 分层**：依赖层只依赖 `pyproject.toml`（改业务代码不失效），uv 下载缓存挂 BuildKit cache mount

  （即使重装也不再联网重下）；代码层在最上，改代码重建为秒级
- **已验证**：容器内跑通完整调研（计划中断 → 审批 → 4 子问题并行取证 → 审校 → 19k 字符报告），

  PG 检查点与 pgvector 记忆写入正常，MCP 工具在容器内正常调用

### 离线部署的三个坑（实测）

| 坑 | 现象 | 修法 |
|---|---|---|
| fastembed 只认 `<cache>/fast-<name>/` | HF 的 `models--...` 目录在离线模式下被判"缓存不完整" | 构建期把快照复制成 `fast-` 布局 |
| MCP 子进程环境被**整体替换** | `stdio_client` 用 `get_default_environment()`，`HF_ENDPOINT` / `FASTEMBED_CACHE_PATH` 全丢 → 模型重新下载失败 | 代码注入 HF 变量 |
| 同上，`DR_*` 也会丢 | 子进程退回 `localhost:5432` → `Connection closed`（报错指向"连接关闭"，实际是配置丢失） | 继承 `DR_*` 前缀 |

验证方式：清空父进程的相关环境变量后，容器内 `search_knowledge_base` 仍能
返回带出处的片段；`--network none` 不可行（知识库要连同机 Postgres）。

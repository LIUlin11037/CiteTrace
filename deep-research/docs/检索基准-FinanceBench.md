# 检索基准：FinanceBench 子集（离线模式）

私有语料 RAG **没有公开基准**（数据本身私有），所以这里用一个**同构代理**：
FinanceBench 的真实美国上市公司 SEC 文件 + 专家标注的 evidence（原文 + 页码）。
本文只谈**检索层**，不含答案生成。

## 0. 一句话结论

> 页面命中@10 从 **14% → 57%**（4 倍），召回上限从 **29% → 90%**；
> 三项改进的分工是正交的：**embedding 决定上限、query 扩展决定能否捞到、rerank 决定排得够不够前**。

## 1. 指标定义（先看这个，否则数字会被误读）

| 指标 | 含义 |
|---|---|
| **页面命中@k** | 前 k 条检索结果里，是否出现 evidence 所在的**那一页** |
| **同文档命中@k** | 是否定位到正确的**文件**（比页面宽） |
| **evidence 文本命中@k** | 检索片段是否包含 evidence 原文（比页面严） |

> ⚠️ **本表的 57% 不是"答案正确率"。** 与论文的 19%/50% 直接比是错的。
> 正确读法：`57%（检索命中）× 85%（Oracle 上限）≈ 48%` 的端到端上限。

页码口径：FinanceBench 的 `evidence_page_num` 是 **0-indexed**（标注 55 → PDF 第 56 页），
三份 10-K 实测全部 +1；不换算会把所有命中判成失败。

## 2. 数据规模

| 项 | 值 |
|---|---|
| 题目 | 21 道（来自 3 份 10-K，开放样本 150 题的子集） |
| 文档 | AMD / American Express / Boeing 2022 10-K，共 **571 页** |
| 切块 | 页级（1 页 1 块，超长页再切），锚点 `p{页号}` |
| 库规模 | 706 块（1024 维） |

## 3. 结果阶梯（逐层加改进）

| 配置 | @1 | @5 | **@10** | @20 | @50（召回上限） |
|---|---|---|---|---|---|
| 本地 `bge-small-zh`（512 维，中文模型） | 0% | 5% | **14%** | 19% | 29% |
| 换 API `qwen3.7-text-embedding-flash`（1024 维） | 10% | 33% | **38%** | 52% | 76% |
| ＋ rerank `qwen3.7-text-rerank`（50 候选） | 24% | 38% | **52%** | 62% | 76% |
| ＋ **query 扩展**（LLM 改写成 3 条财务术语查询，多路 RRF） | 24% | 33% | **48%** | 81% | **90%** |
| **扩展 + 精排（20 候选，融合后只排一次）** | **33%** | **48%** | **57%** | **71%** | — |

同文档命中@10 全程 **100%**（能找对文件，难点在定位到页）。

## 4. 三个可复用的结论

**① embedding 决定召回上限**

中文小模型检索英文财报，@50 只有 29%——**不是"排得不好"，是"根本没捞到"**。
换成多语言模型后 @50 = 76%。

**② rerank 只治排序，不治召回**

单独加 rerank：@1 从 14% → 24%（浅层翻倍），但 @50 **一动不动（76%）**。
它重排已有候选，不会凭空变出没检索到的页。

**③ query 扩展治的是召回**

问题问"流动性是否健康"，页面上写的是 `Current ratio 2.5 / Cash 4,826`——
**没有共同词，向量也就无从匹配**。改写成 3 条财务术语查询后：
@20 从 52% → **81%**，@50 从 76% → **90%**。

## 5. 外部参照（FinanceBench 论文，GPT-4-Turbo）

| 配置 | 结果 |
|---|---|
| 无检索（纯训练知识） | 9% 正确 |
| 共享向量库（多公司混索引，≈ 我们的设置） | **19%** 正确，68% 拒答 |
| 按文档检索（已知是哪份文件） | **50%** 正确，39% 拒答 |
| 长上下文喂正确页 | 79% 正确 |
| **Oracle（完美检索）** | **85%** 正确 |
| 题目构成 | **66% 需要数值推理** |

**读法**：我们的 57% 是检索指标、且比论文的"按文档检索"更难（3 家公司共享索引、
不告诉系统是哪份文件）。Oracle 85% 说明**即使检索完美，仍有 15% 是推理/算术失败**——
所以检索继续优化的边际收益在下降。

## 6. 复现

```bash
# 1) 入库（页级切块，1024 维 API embedding）
python scripts/ingest_kb.py kb_demo/financebench/pdfs --root . --reset

# 2) 基线（单查询）
python scripts/eval_financebench_retrieval.py --ks 1 5 10 20 50

# 3) 加 query 扩展（多路检索 + RRF）
python scripts/eval_financebench_retrieval.py --ks 1 5 10 20 --expand
```

需要的配置（`.env`）：`DR_EMBEDDING_PROVIDER=api` + `DR_EMBEDDING_API_*`、
`DR_RERANK_PROVIDER=api` + `DR_RERANK_API_*`、`DR_KB_TABLE=kb_chunks_qwen`。
PDF 见 `kb_demo/financebench/README.md`（不提交，按 `doc_link` 下载）。

**踩过的两个坑**：① 页码 0-indexed（见 §1）；② embedding API 会 429 限流，
入库需退避重试（已内置）。

## 7. 表格解析：试过，是负收益

| 组 | 配置（Boeing 7 题，@10） | 页面命中@10 |
|---|---|---|
| A | pypdf 抽文本（基线） | **57%** |
| B | pdfplumber 抽文本 + 表格 Markdown | 14% |
| C | pdfplumber 抽文本（无表格） | 14% |
| D | pypdf 文本 + pdfplumber 表格 | 14% |

两个发现：

1. **pdfplumber 的文本抽取比 pypdf 差**（C 组同样 217 块却只有 14%）——它按坐标输出，多栏/表格页容易乱序。
2. **把表格转 Markdown 塞进页面块会稀释语义**：一页 1500 字正文加入 2500 字"| 25,867 | 19,493 |"，
   整块向量被数字噪声拉平，和问题的语义距离反而变大。表格**单独成块**更差（重复 + 争抢名次）。

**结论**：表格解析保留接口（`core/pdf.py`、`--pdf-tables`）但**默认关闭**。
这类"从 100 页里找一个数字"的题本质是**数值定位**，不是语义检索；要突破应换路线
（表格 → 自然语言摘要再嵌入 / 表格 → SQL / 多模态读图），而不是继续调切块。

## 8. 已知边界

- 样本 21 题：单题 = 4.8%，**不要在小数点上做文章**
- 只覆盖 3 份文档；跨文档对账、多轮追问未测
- 检索 ≠ 端到端：答案正确率需要另跑一次生成层评测

## 摘要

本报告回答两个问题：如何让 LLM 稳定输出符合 schema 的 JSON，以及约束解码与提示词约束的差别。**必须先说明证据边界**：本地知识库对这两个问题的核心技术内容覆盖极薄。库内 6 条证据中，没有任何一条给出约束解码的定义、实现路径或实验数据，也没有任何一条给出提示词约束的实测 schema 合规率。可用的只有三类间接材料：Anthropic 关于 JSON schema 语义表达力局限的转述[^1]、本项目「统一走 with_structured_output（pydantic 校验）、禁止 regex 解析 JSON」的工程约定[^2][^3]、以及推理引擎仓库热度[^4]与 agent 失败模式的定性描述[^5][^6]。因此本报告能确认的是「schema 合法 ≠ 语义正确」这一边界，以及若干工程约定与已知风险；**约束解码的机制、学术进展、生态对比、量化差异均须标注为知识库未收录**。

## 一、schema 合规问题的真实边界：结构合法不等于语义正确

在讨论任何技术手段之前，需要先界定「符合 schema」到底约束了什么。库内唯一直接触及这一点的证据，是转述 Anthropic 的观点：JSON schema 只能定义结构上合法的内容，无法表达使用模式——即何时应包含可选参数、哪些参数组合是合理的、API 期望的约定是什么[^1]。

这条论断的方法论含义是：即使一个输出 100% 通过 JSON Schema 校验，它仍可能在语义层面错误（该填的可选字段没填、填了互斥组合、值域符合类型但不符合业务约定）。因此「稳定输出符合 schema 的 JSON」应拆成两层目标：

1. **语法/结构层**：输出可被解析为 JSON，且满足给定 schema 的类型、必填、枚举等约束；
2. **语义/使用层**：参数组合与取值符合调用方的真实约定。

现有证据只对第 1 层提供了工程手段的线索，对第 2 层明确指出 schema 本身无法覆盖[^1]。这一区分是后文比较两类方法的前提：任何只作用于 token 生成过程的机制，其作用域上限就是第 1 层。

## 二、约束解码：知识库未收录其定义与实现

**当前知识库未收录约束解码的核心定义。** 具体而言，以下内容在库内均无来源：logits 掩码（masking）的机制与数学形式化、有限状态机（FSM）/正则表达式路径、上下文无关文法（CFG）与下推自动机的对应关系、将 JSON Schema 编译为自动机的具体流程，以及 grammar-guided decoding 的权威出处。

需要特别澄清两条容易被误读为约束解码证据的材料：

- 来源[^1]讨论的是**工具定义消耗上下文**以及工具选择/参数错误，该片段明确未涉及解码期如何对 logits 施加约束，也未涉及 FSM/CFG/自动机等实现路径[^1]。它属于「schema 作为提示内容进入上下文」的问题域，与「schema 作为解码约束」是两件事。
- 来源[^2][^3]规定本项目所有 LLM 解析走 `with_structured_output`（pydantic 校验），代码库中禁止 regex 解析 JSON[^2][^3]。这是**本项目自身的工程约定**，不是约束解码的权威定义；文档亦未说明 `with_structured_output` 底层是否采用约束解码或语法引导解码[^2][^3]。换言之，这条约定在接口层保证了「有校验」，但在实现层是黑箱，不能据此推断系统已获得约束解码的收益（如首 token 开销、表达力上限）。

因此，关于「约束解码如何实现」这一问题，本报告只能给出结论性判断：**当前知识库未收录该信息**，无法在此展开机制层面的说明。

## 三、提示词约束：库内无合规率数据，仅有相邻语境的失败模式

**当前知识库未收录提示词约束（few-shot、schema 描述、JSON mode、重试/校验修复）的实测 schema 合规率。** 库内没有任何 prompt-only 与约束解码在准确率、延迟、成本上的量化对比。

两条证据常被误用，须明确其不可替代性：

- ToolFailBench 覆盖金融、医学、法律、网络安全、房地产五个领域的 1,000 个任务，用规则分类器加两个 LLM 评判器多数投票，为每条轨迹打四类标签（Tool-Skip、Result-Ignore、Output-Fabrication、Unnecessary-Tool-Use）；在 19 个头部模型上最佳模型达到 86.33% 的 Clean Tool-Use Rate[^5]。该数字是**工具使用清洁率，不是 JSON schema 合规率**，不可替代本问题所需的合规率数据[^5]。
- agentic RAG 语境下的三类生产失败模式——Retrieval Thrash（检索反复但不收敛）、Tool storms（工具调用过度、级联并重试直至预算耗尽）、Context bloat（上下文窗口被低信号内容填满，直到模型不再遵循自身指令）——其根因被归为缺乏预算控制、弱停止规则与对决策循环零可观测性[^6]。这只能作为「重试/校验修复循环」已知风险的**定性旁证**：重试会放大成本，上下文膨胀会导致指令遵循退化；但它属 agentic RAG 语境，非 JSON 输出场景实测[^6]。

对工程实践而言，这条旁证的可用推论是：以「生成—校验—失败则重试」为核心的提示词侧方案，其成本与可靠性风险并非线性，重试次数增加会同时推高 token 成本并可能因上下文膨胀而降低后续指令遵循质量[^6]。但该推论缺少 JSON 场景的实测支撑，属待验证假设。

## 四、两类方法的差别：库内可确认的部分与不可确认的部分

综合上述证据，库内**能够**支撑的差别只有一条，且是作用域层面的：

- 提示词约束（把 schema 写进上下文、few-shot 示例、JSON mode 等）作用于模型的生成倾向，其效果受上下文预算与指令遵循稳定性影响；库内证据显示工具定义本身即构成隐性上下文开销[^1]，且上下文被低信号内容填满会导致模型不再遵循自身指令[^6]。
- 约束解码作用于解码期的 token 选择过程，理论上可在结构层直接排除非法输出；但**其机制、表达力上限与开销在库内无任何来源**，本报告不对其效果作任何量化或机制性断言。

库内**不能**支撑的差别包括：两者的 schema 合规率差异、延迟与首 token 开销差异、对推理能力的潜在损害、对复杂 schema（递归、联合类型、条件约束）的表达力差异。这些均属「当前知识库未收录该信息」。

工程生态方面同样如此：库内仅记录 vLLM 仓库 95,274 stars、Apache-2.0 许可、截至 2026-10-24 仍每日级活跃，SGLang 仓库 37,685 stars、同期高频提交[^4]；但该片段明确未涉及 guided decoding / structured output 功能、schema 表达力或首 token 开销[^4]。Outlines、XGrammar、llguidance、Guidance、Instructor、Pydantic AI、OpenAI Structured Outputs 等其余实现路径在库内零覆盖，无法支撑生态对比结论。

## 五、矛盾与不确定性

**（1）约束解码的定义与形式化：库内无覆盖。** 现有两条相关证据均不相关：一条是 Anthropic 关于 JSON schema 无法表达使用模式的转述，属工具定义语义局限而非解码期约束[^1]；另一条是本项目「禁止 regex 解析 JSON、统一走 with_structured_output」的工程约定，且未说明其底层是否采用约束解码[^2][^3]。库内没有任何来源给出 masking / grammar-guided / pushdown automaton 的定义、形式化或权威出处。

**（2）2024–2026 年 arxiv 学术进展：库内无覆盖。** 两条相关证据均为本项目架构文档中的工程选型约定[^2][^3]，与 arxiv 论文、实验数字、结构化输出是否损害推理能力、grammar 加速等结论完全无关。子问题涉及的相关研究在库内无任何痕迹。

**（3）工程生态与表达力差异：库内仅覆盖 vLLM 与 SGLang 的仓库热度，且该片段明确不涉及 guided decoding 功能[^4]。** 其余实现路径零覆盖，无法支撑「工程生态现状」与「表达力差异」的对比结论。

**（4）提示词约束的实测合规率与两类方法的量化差异：库内无覆盖。** ToolFailBench 的 86.33% 是 Clean Tool-Use Rate，非 JSON schema 合规率[^5]；agentic RAG 的三类失败模式属 agent 决策循环语境，只能作重试放大成本的定性旁证[^6]。库内没有任何 prompt-only 与约束解码的量化对比，也没有主流厂商官方文档的实践建议。

**（5）一处需注意的表述张力。** 来源[^1]指出 JSON schema 无法表达使用模式[^1]，而来源[^2][^3]以 pydantic 校验作为统一解析路径[^2][^3]。二者并不矛盾——pydantic 校验同样只能验证结构层，无法验证第 1 节所述的语义/使用层——但库内没有任何来源讨论该校验路径在语义层的失败率或补偿手段。这一空白意味着：本项目的工程约定解决了「解析可靠性」，但「参数组合是否合理」仍需外部机制（如调用方校验或业务规则），而该机制在库内无记载。

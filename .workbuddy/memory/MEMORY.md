# 项目长期约定（agent workspace）

## Git 提交风格
- 用户的习惯：**简短中文标题，无 Conventional Commits 前缀（feat/fix 等），无长正文**
  - 例：「服务端完成」「初测」「init」「加上 web 演示页，顺手修了几个 bug」
- 提交前先 `git log --format="%s" -10` 看历史风格，按用户风格写；不要默认套 Conventional Commits + 结构化正文
- 需要交代的技术细节写在 README / 架构文档 / 代码注释里，不塞进 commit message
- commit 前先确认是否已推送（`git log origin/main..main`），未推送才允许改写历史

## 分工约定（用户提出）
- 架构核心 / 易错部分由主模型做；外围、低技术力模块可交低端模型
  （原先用 `docs/handoff.md` 写派工契约，2026-10-16 用户确认不再需要，该文件已删除）
- 涉及"先要修后端才通"的外围，主模型自己做完更划算（旧 Web 页即如此：契约先写好，最后仍是主模型实现并修掉 3 个后端 bug）

## 成本意识
- 用户在意 API 花费：全量 26 题基准约 ¥10（deepseek-chat 空闲时段 ~¥0.35/题，高峰翻倍）
- 想验证改动影响时优先"抽 2-3 题 + 与旧数据对比"，而非无脑全量重跑
- 对比实验必须控制变量：跑基准时要与旧数据条件一致（如 `DR_ENABLE_LONG_TERM_MEMORY=false`，因为旧基准跑在 M3 记忆之前）

## 工作顺序约定（2026-10-15 用户明确提出，务必遵守）
- **代码全部改完定稿后，最后才做 Docker 构建 / 部署验证，一次性完成**
- 不要在代码还在改动时中途做构建验证：之后任何代码改动都会让镜像作废，在慢网络下逼出重复构建
  （2026-10-15 教训：中途验完 Docker 后又改代码 + 改 Dockerfile，导致三次重建、每次十几分钟下载）

## 改动边界（用户强调）
- 只做用户明确要求的改动。需要改构建文件（Dockerfile / compose）、配置或删除功能时，先说明并征得同意再动手
- 不要顺手"优化"用户没让改的东西；不要给用户的选项菜单式反复征询，直接给一个判断 + 说明

## 长命令执行纪律（血泪）
- 长命令**不要设超时**（会被杀、白跑一轮）；用后台任务 + 重定向到日志文件
- 输出**绝不要管到 `tail`**（会缓冲到命令结束，看起来像卡死，曾因此误杀一次正常构建）
- 判断构建是否在推进：看日志文件的 `Downloaded/Downloading` 行与时间戳，而非缓存大小（整层完成前不变）


## 数据层与架构底线（2026-10-16 用户强调，务必遵守）
- **统一使用 PostgreSQL**：检查点与 pgvector 长期记忆同库。代码默认、`.env.example`、compose 一律 postgres
- sqlite 只允许作为**显式开启**的零依赖后备（`DR_CHECKPOINT_BACKEND=sqlite`），**不许当默认、不许拿它绕问题**
- 环境不通（如 Docker 没起、PG 连不上）时的正确做法：**如实报告 + 等用户处理**，不要自作主张降级后端

## 协作方式（用户多次强调，务必遵守）
- 改任何东西前先征得同意，尤其是**配置/构建文件/删除功能**
- 遇到阻塞别自己找替代路径"绕过去"，先问
- 不要给选项菜单式反复征询；给一个判断 + 说明，但要**先获得同意再动手**
